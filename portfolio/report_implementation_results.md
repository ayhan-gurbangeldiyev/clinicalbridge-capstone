## What was built (as implemented)

A five-component multi-agent system that turns one simulated RPM alert into a Clinical
Context Brief:

- **Orchestration — LangGraph `StateGraph`.** Nodes: triage → (CRITICAL? escalate :
  EHR ∥ Anamnesis) → synthesis. EHR and Anamnesis run in parallel (fan-out from triage,
  fan-in at synthesis); CRITICAL alerts bypass synthesis and escalate immediately. A shared
  `session_log` (with an `operator.add` reducer) records every step for auditability.
- **Agents — LangChain.** Each agent is a `ChatPromptTemplate | gpt-4o | PydanticOutputParser`
  chain producing a schema-validated object (`schemas/`).
- **RAG — ChromaDB.** Per-patient EHR collections, `text-embedding-3-small` embeddings,
  top-k cosine retrieval surfaced to the EHR agent.
- **Tools & memory — Module 7.** `agents/tools.py` exposes three LangChain tools
  (`vector_store_search`, `alert_classification`, `rpm_trend`, `parse_anamnesis`); the
  Anamnesis agent uses a per-patient entity memory (`agents/memory.py`).
- **Observability — LangFuse.** A callback handler attached at the graph invocation traces
  every agent call (prompt, output, latency, tokens) into one trace tree, tagged with
  `patient_id` / `prompt_version` / `scenario`. Degrades gracefully without keys.

## Dataset (all simulated)

12 fictional patients across hypertension, type 2 diabetes, and heart failure, in three
formats: EHR documents (`data/patients/`), anamnesis self-reports (`data/anamnesis/`), and
14-day RPM time-series (`data/rpm/`, generated by `generate_rpm.py` with scenario-appropriate
trends). Five end-to-end scenarios each carry a gold-standard brief.

## Reflection — what the iteration taught us

The triage prompt's three-version arc is the clearest prompt-engineering lesson, and it reads
differently on a small vs a large model:

1. **v1 over-escalated** — echoed the device's "URGENT" label (FA-001, misclassified the
   benign glucose blip).
2. **v3** instructed independent re-evaluation, fixing the false alarm — but exposed a subtler
   gap: judging a deteriorating heart-failure patient from a single +1.7 kg reading looked
   mild, so it under-escalated (FA-004).
3. **v4** gave triage the *trajectory* via an RPM-trend tool: a sustained climb escalates, an
   isolated spike does not.

On the small **gpt-5.4-nano** model this arc moved triage 60% → 80% → 100% with no model
change — prompt engineering alone closed the gap. On **gpt-4o** the model already scores 100%
from v1, so the same prompts act as an explicit, auditable correctness guardrail rather than
an accuracy lift. Broader takeaways: (a) better reasoning can *trade* one failure mode for
another, so evaluation must be continuous; and (b) prompt engineering delivers the most value
on smaller/cheaper models and remains a safety net on larger ones.

> Honesty note: an earlier draft mislabelled the model as gpt-4o while the deployment was
> actually gpt-5.4-nano. The numbers above are from the corrected gpt-4o runs; the nano
> figures are kept because they make the prompt-iteration contribution visible.

## Known limitations

LLM hallucination risk is non-zero despite a measured 0% on these scenarios; simulated data
(and synthetic RPM trends) cannot capture real-record messiness; gold standards are
author-defined; and synthesis clinical accuracy (89%, LLM-judge) lands just under the 90%
target — reported honestly rather than forced (see FA-005). See `bias_and_limitations.md` for
the bias discussion. This remains an educational prototype — not for clinical use.
